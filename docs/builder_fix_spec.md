## BUG 1: NHA BLANKING (CRITICAL — Lines 1988-2009)

### Symptom
All NHA values in MIUL_test.xlsx are blank (nan) except Row 2 which has "test".

### Root Cause
Phase 3e "SecPayMIUL compliance" normalization at lines 1988-2009 blanks NHA for every row where `Parent != 2`:

```python
# Line 2002-2008 (CURRENT - BROKEN)
if parent == 2:
    row["NHA"] = miul_acronym   # Only MER07540-001 gets this
else:
    row["NHA"] = ""             # ALL 40 other rows get blanked
```

With the corrected DT JSON, only MER07540-001 (the top-level assembly) has Parent=2. Every other row has Parent=3, 4, 5, etc. So 40 out of 41 rows get their NHA wiped.

### The SecPayMIUL Spec Misunderstanding
The comment says "NHA should be blank for subparts" but this is wrong. In a real MIUL, NHA carries the **parent drawing number** for every row. The Parent column carries the **index** of that parent row. Both are needed. The MAPTIS import uses NHA to validate hierarchy, and Parent to order the tree.

### Fix
**Remove Phase 3e entirely.** The NHA values set in Phase 3a (lines 1816-1889) are already correct — they come directly from the DT JSON `nha_map`. Phase 3c uses those NHA values to correctly calculate Parent indices. After Phase 3c completes, both NHA and Parent are correct. Phase 3e then destroys the correct NHA values.

```python
# DELETE lines 1988-2011 entirely (Phase 3e block)
# The NHA values from Phase 3a are already correct.
# Phase 3c already used them to calculate Parent.
# There is NO reason to overwrite them.
```

### Verification
After removing Phase 3e, the output should show:
- MER07540-001: NHA="DMLLV", Parent=2
- MER07543-001: NHA="MER07540-001", Parent=3
- MER07560-001: NHA="MER07543-001", Parent=4
- MER07564-001: NHA="MER07563-001", Parent=6
- (etc — every row has its actual parent drawing number as NHA)

## BUG 2: MATERIAL KEY MISMATCH (CRITICAL — Line 666 vs Line 1399)

### Symptom
All Designation fields are blank for EPL children in `build_miul()` pipeline, even though pdfplumber correctly extracts material values from EPL tables.

### Root Cause
Two different functions use different keys for the same data:

**`_convert_text_result()` at line 666** writes:
```python
"material": p.get("material", ""),
```

**`_process_assembly()` at line 1399** reads:
```python
raw_material = correct_ocr_errors(part.get("material_callout", "") or "")
```

Key written: `"material"`
Key read: `"material_callout"`
Result: Every EPL material silently drops to empty string.

### Fix
Change line 666 to match what line 1399 expects:

```python
# Line 666: Change "material" to "material_callout"
"material_callout": p.get("material", ""),
```

Also add the spec key that line 1401 reads:
```python
# Line 1401 reads: part.get("spec_callout", "")
# Verify that _convert_text_result outputs "spec_callout" or add it
```

Check line 667 area for any similar key that might map spec data. If there's no spec key being output from _convert_text_result, add one.

### Scope
This bug affects the `build_miul()` / `build_miul_from_directory()` pipeline only. The `merge_dt_and_parts()` pipeline reads from Parts JSON using key `"material"` at line 1836, which matches. However, if Parts JSON was generated by code that calls `_convert_text_result`, the same mismatch could propagate.

## BUG 3: ASSEMBLY HEADER DESCRIPTIONS BLANK (MODERATE — Phase 3a)

### Symptom
Assembly header rows (MER07540-001, MER07543-001, etc.) have blank Part Description in MIUL_test.xlsx.

### Root Cause
In `merge_dt_and_parts()` at line 1833:
```python
title = drawing_info.get("title") or part_info.get("description") or entry.get("title", "")
```

The fallback chain is: drawings dict → parts dict → DT entry title. If neither `drawings` nor `parts` dicts have data for the assembly drawing number, it should fall back to the DT entry's `"title"` field.

The corrected DT JSON has titles for every entry:
```json
{"drawing_number": "MER07543-001", "title": "SHAFT ASSEMBLY, 10 INCH VALVE", ...}
```

### Investigation Needed
Check whether `entry.get("title", "")` is actually being reached. The issue might be that `drawing_info.get("title")` returns an empty string `""` (which is falsy in the `or` chain only if exactly empty string... actually `""` IS falsy in Python, so the chain should fall through).

**Most likely cause:** `drawing_info` or `part_info` contains an entry with `"title": ""` or `"description": ""`, and Python's `or` treats empty string as falsy, so the chain SHOULD fall through to `entry.get("title")`. If descriptions are still blank, the DT JSON entries might not have the `"title"` key.

### Verification
Print debug: add `LOGGER.debug(f"Title for {dwg_num}: drawing={drawing_info.get('title')!r} part={part_info.get('description')!r} dt={entry.get('title')!r}")` at line 1833.

The corrected DT JSON DOES have titles, so if merge_dt_and_parts is given this JSON, titles should populate. If they're blank, the issue is that the DT JSON used during the actual run was different (extracted DT, not the corrected one).

### Fix
Ensure the corrected DT JSON (`MER07540-001_corrected.json`) is used as `dt_json_path` input to `build_miul_2phase()`. The title fallback chain at line 1833 should work correctly with this data.

## BUG 4: NOTE REFERENCES IN PART NUMBERS (MINOR — Text Extraction)

### Symptom  
Part numbers have EPL note callouts appended: "WSM-137-C86 10.", "WHM-275-S86 5.", "EH-22-C86 6."

### Root Cause
In `text_extract.py`, `_parse_epl_row` joins columns that include the note reference column. The note number (like "5.", "6.", "10.") sits in an adjacent column and gets concatenated with the part number.

### Fix
In `builder.py`, add a post-processing step to `correct_part_number()` or add a new cleanup:

```python
import re

def strip_note_reference(pn: str) -> str:
    """Remove trailing EPL note references like ' 5.' or ' 10.' from part numbers."""
    return re.sub(r'\s+\d{1,2}\.\s*$', '', pn).strip()
```

Apply this after `correct_part_number()` at line 1396 in `_process_assembly()`:
```python
part_number = strip_note_reference(correct_part_number(part.get("part_number", "")))
```

And in `merge_dt_and_parts()` wherever part numbers are processed from the Parts JSON.

## BUG 5: STANDARD HARDWARE NOT APPEARING (MODERATE — merge_dt_and_parts)

### Symptom
Standard hardware parts (MS, NAS, AN prefixed) from assembly EPLs are missing from MIUL output.

### Root Cause
In `merge_dt_and_parts()` Phase 3b (lines 1893-1957), standard hardware is only added from the Parts JSON if it wasn't already in the DT. But the DT JSON only contains project-specific MER parts, not standard hardware. So standard hardware SHOULD be added in Phase 3b.

### Investigation
Check whether the Parts JSON actually contains standard hardware entries. If `parts_json["parts"]` only has MER part numbers (because the extract only captured assembly-level data, not individual EPL line items), then there's nothing to add in Phase 3b.

The Parts JSON should contain entries like:
```json
{
  "parts": {
    "MS21209C1610": {"material": "CRES", "description": "SCREW", ...},
    "NAS1352N04-16": {"material": "A286", ...},
    ...
  }
}
```

If it doesn't, the problem is upstream in `extract_parts_json()` which needs to capture individual EPL row items, not just the assembly-level summary.
